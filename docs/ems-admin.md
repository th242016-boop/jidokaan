## 운영자가 처리하는 순서

1. 신규주문에서 결제, 확정 디자인, 사이즈, 수량, 배송지와 연락처를 확인한다. 기존 상세 주문 화면의 정보는 유지한다.
2. 주문별 **발송 준비**, 또는 여러 주문을 선택한 뒤 **선택 주문 발송 준비**를 누른다. 결제 완료 주문만 대상이며 미결제·취소·처리 중인 클레임 주문은 차단한다.
3. EMS 준비 화면에서 불러온 수취인 정보를 확인하고 영문 주소·영문 품명·실제 HS/HTS 코드·원산지·품목별 금액·실측 무게·포장 크기를 확인한다. 알 수 없는 값은 자동으로 채우지 않는다.
4. 실제 상자 개수에 맞춰 소포를 나누고 품목 수량·신고 금액을 배분한다. 한 주문의 모든 소포에 담긴 상품 합계가 주문과 일치해야 한다.
5. 지원되는 경우 공식 TXT를 내려받고, **우체국 스마트접수**를 열어 신청한다. 방문수거를 선택하지 않고 창구 직접 반입 방식으로 진행한다. 파일 다운로드나 링크 클릭만으로 우체국에 접수되지는 않는다.
6. 우체국에서 확인한 접수 참조와 우편물번호를 소포별로 입력하고 실제 접수 완료를 확인해 저장한다. 이때는 **우체국 제출 대기**이며 배송중이 아니다.
7. 포장한 소포를 직접 우체국 창구에 맡긴 뒤 해당 소포의 **발송**을 확인한다. 실제로 맡기지 않은 소포는 발송 처리하지 않는다.
8. 배송조회 연동이 승인·검증된 뒤에는 우체국 기록을 조회하여 상태를 반영한다. 여러 소포 전부가 실제 배달완료일 때만 주문 전체가 배송완료다.

현재 자동화되지 않은 단계는 우체국 로그인, 스마트접수 입력/업로드, 우체국 제출, 접수 결과 입력이다. 실제 배송조회도 키 설정과 실응답 검증 전에는 수동 확인이 필요하다. 이 제한을 숨기거나 연결 완료라고 표시하지 않는다.

## 상태와 화면

| 주문 기본 탭 | 저장된 주문 상태 | 의미 |
| --- | --- | --- |
| 전체 | `paid` / `ready` / `shipped` / `done` | 결제 완료부터 배달 완료까지 기본 업무 목록. 미결제·취소·과거 구매확정/반품/교환은 별도 접근 |
| 신규주문 | `paid` | 결제 완료 후 아직 발송 준비하지 않은 주문 |
| 발송준비 | `ready` | EMS 정보 확인부터 우체국 제출 대기까지 |
| 배송중 | `shipped` | 실제 창구 인계된 소포가 있는 주문, 미배달 소포 존재 |
| 배송완료 | `done` | 모든 소포에 우체국 배달완료 근거가 있는 주문 |

입금대기(`wait`)·취소(`cancel`)는 예외 처리에서, 구매확정(`confirmed`)·반품(`return`)·교환(`exchange`)은 별도 이력에서 볼 수 있다. 기존 코드를 삭제하거나 과거 기록을 일괄 재분류하지 않는다.

| 소포 상태 | 표시와 다음 조치 |
| --- | --- |
| `preparing` | EMS 정보 확인. 누락 항목 보완 |
| `registration_unknown` | 접수 여부 확인 필요. 우체국 기존 신청 내역부터 확인 |
| `registration_failed` | 접수 실패. 실패 내용을 확인하고 보완 |
| `awaiting_dropoff` | 우체국 제출 대기. 사전접수만 완료된 상태 |
| `in_transit` | 배송중 |
| `customs_delay` | 통관 지연. 완료로 집계하지 않음 |
| `delivery_failed` | 배달 실패. 완료로 집계하지 않음 |
| `returned` | 반송. 완료로 집계하지 않음 |
| `delivered` | 실제 배달완료 근거 확인 |

조회불가·응답 오류는 최근 조회 결과에 별도로 표시하고, 기존의 마지막 정상 배송 기록을 지우지 않는다. 과거 배송완료/구매확정 주문을 다시 배송중으로 돌리지 않는다. 기존 주문에 단일 송장만 있고 새 소포 정보가 없으면 기존 기록을 읽기 전용으로 보존한다. 실제 인계일이나 소포 내역을 추측한 자동 이관은 하지 않는다.

## 신고 정보와 파일 내보내기

- 사용자 승인 포장 크기인 410×310×150mm는 준비 화면의 참고 기본값으로만 쓴다. 실제 상자가 다르면 수정한다. 과거에 말한 “1.5kg 이하”를 개별 소포 실측값으로 대신 입력하지 않는다.
- 판매 상품은 상품으로 신고한다. 선물/견본으로 바꾸거나 금액을 낮추는 기능을 만들지 않는다. 배송료와 상품 신고금액은 별개이며 기존 주문 결제액·할인 내역을 확인한다.
- 영문 품명, 실제 상품분류, 원산지, 순중량과 포장 포함 총중량은 관리자가 확인한다. 복싱화라는 이유만으로 소재별 분류를 단정하지 않는다.
- 주소가 영어처럼 보인다는 사실은 실제 배송 가능 주소를 검증했다는 뜻이 아니다. 도시·주·국가·우편번호를 고객 주문 원문과 대조한다.
- 공식 입력 규격의 TXT는 `|` 구분 25개 필드다. 수취인/국가/우편번호/상세주소/도시/주, 전화번호 구성, 이메일, 세금식별번호, 보험·물품 구분, 품명·분류·수량·금액·통화·순중량·원산지 순서다.
- `exportEmsTxt`는 **소포당 신고 품목 1개만** 자동 내보낸다. 여러 품목 소포는 오류로 안내하며 공식 엑셀 양식 또는 스마트접수에서 직접 입력한다. 여러 품목을 한 품목으로 합치거나 같은 소포를 여러 줄로 복제하여 수량을 부풀리지 않는다. 이미 접수했거나 결과가 불확실한 소포는 재접수용 파일에 넣지 않는다.
- 공식 안내는 xls/xlsx/txt, 1MB 이하, 최대 300명, 비서류 세관 품목 최대 4개를 안내한다. 미국행은 HTSUS 조회 및 접수 가능 여부를 우체국에서 다시 확인한다.
- 내려받은 파일에는 고객 개인정보가 있으므로 공개 저장소·공용 캡처·인수인계 패키지에 넣지 않는다.

사용자 승인 없이 새 가입·계약·결제·API 키 생성·권한 확대·상시 접근을 설정하지 않는다. 키를 채팅이나 인수인계 문서에 적지 않는다. 실제 고객 정보의 우체국 전송 시험은 주문번호, 수취국, 전송 항목, 수행할 접수/조회 동작을 먼저 제시하여 별도 확인받는다.

## 배송조회 연결 준비

예정/구현 변수는 `EPOST_TRACKING_SERVICE_KEY`, `EPOST_TRACKING_ENABLED`, `EPOST_TRACKING_HTTPS_VERIFIED`다. 모두 서버 전용이며 프런트엔드 번들에 포함하면 안 된다. 인증키가 있다는 이유만으로 활성화하지 않는다.

공식 공공데이터 문서의 URL은 HTTP로 표시돼 있다. 코드에서는 HTTPS만 허용하며, 이전 키 없는 HTTPS 확인은 503 응답으로 실제 사용 가능성을 검증하지 못했다. HTTP로 키와 우편물번호를 전송하는 우회는 하지 않는다. 우체국이 지원하는 안전한 경로를 확인한 뒤 승인된 시험 번호로 성공 응답을 확인해야 한다.

어댑터는 성공 여부, 요청/응답 번호 일치, 우체국의 명시적 배달완료 상태와 날짜를 확인한다. 임의 클라이언트 JSON, 단순 경과 시간, 빈 응답을 배달완료 근거로 쓰지 않는다. XML 크기·시간 제한과 DTD 거부를 적용한다. 조회 실패 시 기존 근거를 보존한다.

주기 실행은 별도 작업이다. 향후 스케줄러를 추가하려면 호출 한도·개인정보 접근·장애 재시도·완료 소포 제외·중복 실행 잠금·서버 로그의 비밀 제거를 정하고 사용자 승인을 받아야 한다. 조회 버튼을 구현했다고 주기 자동조회가 켜졌다고 보고하지 않는다.

| `src/lib/ems-workflow.ts` | 상태 전이, 누락·수량·금액 검증, 내보내기 |
| `src/lib/ems.server.ts` | 주문 조회, 버전 비교 저장, 중복 송장 방지, 조회 결과 반영 |
| `src/routes/api/ems.ts` | 관리자 인증 후에만 EMS 기능 실행 |

| `src/components/admin/ems-preparation.tsx` | 소포별 정보·접수·인계·조회 UI |

기존 `StoreOrder`에 선택적인 `fulfillment`를 추가한다. 과거 주문에는 없을 수 있다. 원본 주문·결제·고객·디자인 스냅샷을 대체하지 않는다. 별도 소포 송장 소유권 테이블은 추가 방식이며 기존 테이블을 지우지 않는다. 고객용 주문 응답에서는 내부 EMS 편집·감사 정보를 제외한다.

`/api/ems`는 기존 관리자 세션을 사용한다. GET은 Bearer 헤더로 인증하며, POST는 Bearer 헤더 또는 본문 token으로 인증한다. 개인정보와 토큰을 URL에 새로 붙이지 않는다.

| 요청 | 입력/결과 요약 |
| --- | --- |
| GET `?id=주문ID` | 주문, 연결 가능 상태, 누락 항목. id가 없으면 연결 가능 상태만 반환 |
| POST `prepare` | `ids[]`. 주문별 성공/실패를 반환하여 일부 실패를 숨기지 않음 |
| POST `save` | `id`, `version`, `operationId`, 수취인·소포. 임의 배송상태/조회 근거는 수용하지 않음 |
| POST `register` | 소포 ID, 우편물번호, 접수 확인 근거, 확인 체크 |
| POST `uncertain` / `failed` | 소포 ID와 결과 메모 |
| POST `reconcile` | 공식 기존 접수 확인 후 `registered` 또는 `not_registered`, 근거 및 확인 체크 |
| POST `handover` | 실제 인계한 소포 ID 목록과 확인 체크 |
| POST `track` | 소포 ID와 해당 번호 조회 동의. 서버가 조회한 근거만 상태 반영 |
| POST `export` | `ids[]`, 파일 이름·본문·MIME 반환. 외부 전송을 하지 않음 |

편집/상태 변경/조회 요청은 공통으로 현재 버전과 작업 ID를 보내며, 버전 충돌은 409로 반환한다. 같은 작업 ID를 다른 내용으로 재사용하면 충돌로 거부한다. 단순 조회 실패를 접수 실패와 혼동하지 않는다.

저장은 주문 스냅샷과 SQL 상태 열을 함께 비교하여 오래된 화면이 새 변경을 덮어쓰지 못하게 한다. `operationId`와 동일 작업 내용으로 반복 저장을 식별하고, 같은 우편물번호가 서로 다른 소포/주문에 들어가지 않게 한다. 과거 단일 송장과도 대조한다. 레거시 상태 변경이나 취소 승인 경로가 새 보호 장치를 우회하면 안 된다.

접수 응답이 불확실하면 즉시 재접수하지 않는다. “접수 여부 확인 필요”로 남기고 우체국 기존 접수 내역 확인 근거를 기록한 뒤 미접수 확인 또는 기존 접수번호 연결을 선택한다. 현재 앱은 실제 접수 요청을 보내지 않으므로 외부 스마트접수에서 사용자가 수동으로 같은 신청을 반복하는 것까지 막지는 못한다.

## 2026-10-24 후속 변경 — 관리자가 확인한 배송완료 처리

- 사용자의 추가 요청에 따라 배송중인 주문을 선택해 관리자가 배송완료로 처리하는 경로를 추가한다. 위의 “우체국 기록만으로 완료” 설명은 자동조회 경로의 원칙으로 유지하고, 명시적 관리자 확인을 별도 근거로 허용한다. 시간 경과만으로 완료시키는 기능은 아니다.
- 관리자가 선택한 주문의 모든 소포를 배송완료 처리하기로 명시적으로 확인한 뒤 처리한다. 미결제·미발송·취소·진행 중인 클레임 주문은 대상이 아니다. 일부 주문의 실패가 다른 주문의 성공으로 가려지지 않게 결과를 주문별로 표시한다.
- 새 소포 구조에서는 모든 소포에 송장번호와 유효한 창구 인계 기록이 필요하다. 아직 준비·접수 중인 소포는 완료를 막는다. 기존 통관 지연·배달 실패·반송 기록이 있더라도 관리자가 주문 전체를 완료 처리하기로 확인하면 수동 완료를 허용하되, 과거 운송사 조회 근거는 보존한다. 새 소포 구조가 없는 과거 주문은 배송중 상태와 기존 송장번호를 확인하고, 소포 정보를 임의로 생성하지 않는다.
- 관리자 GET `/api/ems?id=...`는 현재 주문의 서버 계산 `revision`을 반환한다. POST `complete_delivery`는 `id`, `version`(소포 구조가 없으면 0), `revision`, `operationId`, `confirmed: true`를 받는다. 일괄 처리는 주문별 요청으로 수행한다. 서버는 최신 상태·버전·스냅샷을 비교하고 동일 작업 반복을 식별한다.
- 주문의 `deliveryCompletion` 및 수동 완료 소포의 `manualDelivery`에 `source=admin_confirmation`, `recordedAt`, `operationId`를 기록한다. `recordedAt`은 관리자 확인 기록 시각이며 실제 배달 시각이 아니다. 우체국의 `deliveredAt`이나 조회 근거를 만들거나 바꾸지 않는다. 이미 우체국 배달완료 근거가 있는 소포는 그 출처를 유지한다.
- 실제 완료 주문을 다시 배송중으로 되돌리지 않는다. 기존 고객 디자인·결제·주소·알림 설정은 유지하며, 이 작업은 우체국 API 신청·접수·배송조회 연결을 수행하지 않는다. 자동조회 키와 주기 실행은 여전히 미연결이다.
- 직전 수정 `f994734dc485a6062872580967f8f3481e7c98e8`은 Railway `f9448ba1-52db-43b6-8e46-cc4201b377ca` SUCCESS 및 실제 관리자 화면 확인을 마쳤다. 이번 수동 배송완료 변경의 최종 시험·커밋·운영 배포·UI 확인은 완료 후 별도 이력에 기록하며, 이 문단 작성 시점에는 확정하지 않았다.
